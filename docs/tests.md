# Tests

```sh
go vet ./... && go test ./...                 # no Docker: logic, rulesets, the probe against a local server, views without a window
go test -tags integration -timeout 30m ./integration/      # against the Colima profile
```

The integration tests judge the gate from outside. The **TUN capture**, a packet capture on the sandbox's TUN device, records what the sandbox actually sent, and a test fails if a packet came from an address other than the sandbox's own, went to an address that is not public, or was anything but TCP or a name query to the resolver; while a gate is locked, anything but the probe's own packets; with no Interface in use, anything at all. What a sandbox must not reach is tried as a connection whose outcome is read (answered, closed, refused or timed out), beside a listener on every address of this Mac that counts what arrives and must count nothing. What the Carrier holds for a sandbox is read from the Mac's own list of its sockets.

The tests of Shared Folders use real ones, under names of their own that begin with `test-`, and skip where the VM was started without its mount.

That the app keeps no key is a test of the config's type: no field of a config, however deep, names a variable, a key, a token or a secret, so its file holds none.

The **MCP registries** are tested on files: each of the seven is written in its agent's shape and read back; a JSON registry with an account, projects and servers of its user's keeps every one of them in its place and its text, and a TOML one every line and comment, a multi-line string that looks like a table among them; a stale entry of the app's goes, with no list kept; and a file with comments, a trailing comma or half its text, and a TOML file with a mistake, are left byte for byte, and said.

The **Host Tool Wall** is tested where it is, with no Docker. The test's own program is started as a Host Tool and tries, from inside, what a tool may and may not do: read a file outside its two folders, list your home, write outside, connect to this Mac, listen, ask this Mac's name, name another process, list the volumes under `/System/Volumes`, run a setuid program, list `/Applications`, read an application its sandbox is not given, ask the name its user logged in under, ask where a file outside is by its number, ask a socket about an interface, open the kernel's network policy, make memory that this Mac's programs share; and what it must be able to do, an Allowed Application read and run among it. The same program is then run with no Wall, where every one of those succeeds, so that each refusal is known to be the Wall's. Other tests hold the launch: the environment, the folder a run starts in and a link out of it, the bound on output, the time limit and the end of every process a run started, a sandbox's requests side by side, one too many refused, one whose asker left ended. The Link is tested apart, with stand-ins for what answers: asks side by side, withdrawn, refused for a sandbox that is given nothing of their kind, and a line that is no ask, which ends it. One reads the Wall as it is written, and fails on a rule that allows a network, a service beyond the GPU's own, a write or an extension beyond the two folders, a folder to run programs from beyond the Wall's own and the GPU's, `/Applications`, a message to the kernel beyond the one that reaches the hardware's registry with the GPU, or a property of a device that is not the graphics device or its surfaces; and on each thing closed by name that is closed no longer. One holds the rules of the Allowed Applications: one for each, of one shape, with the GPU a second, the application named by a parameter and in no rule; that a link in a folder of applications is neither listed for a Setup nor served, and is not read under the Wall. With a C compiler on this Mac, one builds a program under the Wall that asks the hardware's registry: without the GPU every question is refused, with it all but finding a device by its class, and with no Wall none. Where this Mac has a receipt of Homebrew's, one sees that it is not read under the Wall, nor the files that start a package's service, and that the package's folder is. One starts the test's own program some thirty ways, by its path and by a name in a folder that stands for Homebrew's, and says for each whether the program has the GPU Shim: through `sh`, bash and zsh, scripts of each, `env`, `xargs`, `find`, `time`, `make` and `python3`; the ways that stay without it are rows of that test too, so that one which begins to work, or stops, is seen. With a Swift compiler and ffmpeg on this Mac, two more build a Metal program under the Wall and compute with it on the GPU, with a binary archive, and encode and decode video with the hardware; they are skipped where those are missing; the video is encoded once more through `sh`, bash, zsh, `find` and `env`, and judged by `ffprobe`. The way there and back is an integration test: a call made in a workstation as an agent's client makes it runs a program on this Mac, which writes what the workstation then reads. And with the virtual Interface and `.env`, an experiment asks a model for two things only this Mac can give, and judges by the files it left.

A gate whose probe goes unanswered is tested without leaving this Mac: the sandbox's one Allowed Interface is loopback, where the Carrier's connections go nowhere. The tests of a gate that opens, and of one that sees an address it does not expect, allow the Interface an unbound socket of this Mac leaves by, ask a public service what address they are seen at, from the test process and from the sandbox, and expect the same answer. They reach the three probe URLs a new sandbox starts with (`icanhazip.com`, `ifconfig.me`, `checkip.amazonaws.com`), `api.ipify.org`, `ipinfo.io`, `github.com`, `one.one.one.one` and a Hetzner speed-test file, and skip where this Mac reaches none of that. They cut a download four ways: a Host Condition fails, the gatekeeper is killed, the gatekeeper's process is stopped while `tun` runs on, the gatekeeper's container is paused. And they end a sandbox's `tun`, and another's Carrier, beside a third that must see none of it.

The third expectation is tested on this Mac's physical Interface with this Mac's physical exit addresses said by the test, so that each thing the gate does with them is seen against a real gatekeeper, a real Carrier and the internet: not known, the gate is locked for it and the capture holds the probe's packets alone; with another address said to be this Mac's physical exit address, the gate opens on an address nobody listed; with the address the sandbox leaves from said to be this Mac's physical exit address, under a download, the gate locks on the mismatch, the download is cut and the Carrier holds no connection; and not known again, under a download, cuts that too. A sandbox that lists its addresses is seen not to ask. The real Host Watchdog is asked for this Mac's physical exit address and must answer with the address the test process is seen at: on a Mac with a VM's host-only bridge, that it answers at all says the bridge was left out.

The fourth expectation, this Mac's physical exit address, is tested the same two ways. With this Mac's physical exit addresses said by the test: not known, the gate is locked for it; with another address said to be this Mac's physical exit address, it is locked on the mismatch, which names the address the sandbox leaves from; with that address said to be this Mac's physical exit address, it opens; and when the address stops being this Mac's physical exit address under a download, the download is cut. The heartbeat is seen to ask with no interface left out. With the real Host Watchdog, a sandbox that leaves by this Mac's physical Interface opens, and stays open over the Watchdog's next Rounds.

**An image's build** is tested against a daemon of the tests' own, which keeps where the steps of each build were to run: the gatekeeper's image on the VM's network, a workstation's in its sandbox's namespace, and none while that sandbox's gate is locked (`internal/orchestrator/build_test.go`). Against Docker, a sandbox with an open gate builds the image of a pack that is new with each run, and the pack's step writes down what it had: loopback and the TUN device and no other device, the sandbox's resolver file, the address it was seen at, which is the sandbox's, and a refusal at once of the address the VM has for this Mac, where the backstop would have left it unanswered. A sandbox whose gate never opens, started with a pack that is new, does not start: it says that its image is built by way of its gate and why the gate is locked, and leaves no image and no container. Since an image is built by way of an open gate, a test of a gate that stays locked has its image built first where it is not there, by a sandbox whose gate opens (`built`, in the harness), and so needs the internet when its image is new.

**Stand-in addresses** are tested in the Carrier, the gate, the ruleset's text and the probe's dialer, each with what it must not do beside what it must. The Carrier carries to the range only by an Interface that answers names with them, never to this Mac's own address in it, and to none by another Interface. The gate tells the kernel whether the range is reached only when the Interface in use changes, in the order that ends the lease, and says it again where the kernel refused. A probe connects to a stand-in address only when it says that it reaches them, and what is kept of a name is kept apart for such probes. Against Docker, three sandboxes leave by this Mac's physical Interface, which hands out none (`integration/standin_test.go`): where the Setup says that names are answered so, with a Hold and without, the kernel's set holds the range, the ruleset is still found as it was loaded, a connection to a stand-in address is on the device and the Carrier takes it, and every other address that is not public is refused as before; where the Setup does not say so, the ruleset has no such set, the connection is refused at once, and nothing for it is on the device. Two more tests need a way out that answers names with stand-in addresses, a tunnel by which what is bound to no Interface leaves this Mac, and skip without one (`integration/standin_tunnel_test.go`). By the tunnel, a sandbox whose Setup says so is given a name at a stand-in address, connects to it and is answered, and its gate opens, while one whose Setup does not say so opens no gate. By a port of this Mac's beside the tunnel, a workstation's image is built, its step given the name's own address.

A sandbox's **Home** is tested on sandboxes whose gate stays locked, since a Home needs no network: `/workspace` is the agent's, with a home directory's mode, on the VM's disk; a file, a login and an installed program are there after a stop and a start, and the login shell finds the program by its name; the Home is not deleted while its sandbox runs, by the app or by Docker; another sandbox sees none of it; what a pack wrote under `/workspace` in its image is not in a Home; and the empty folder a Shared Folder left in a Home is gone at the next start without one. `/tmp` is tested beside it: a volume on the VM's disk and no memory, anyone's to write, from which programs run; its volume is gone after a stop, and after the launch that finds a sandbox whose app died, while the Home is still there; and the next start has another, empty. Every test's sandbox starts on an empty Home and leaves none: a test deletes a Home by its own sandbox's ID, and never one whose ID is shaped like the app's.

**Agents installed by hand** are tested with the makers' real installers, through an open gate, typed into a login shell as you would type them in a Pane; their command lines are in the tests alone (`integration/agents_test.go`). One test installs each of the seven agents in turn in one sandbox, and fails for any whose installer no longer leaves its executable where a login shell finds it. It then has each find the server `sandbox` in its own registry, where the supervisor wrote it: by the command with which the agent lists its MCP servers, for the five that have one (Claude Code, Codex, Grok, OpenCode, Antigravity), and by starting it, for the three that start their servers when they are started on a terminal with nobody logged in (Kimi Code, once its folder is trusted, Pi and Antigravity). It starts each by its name in a Terminal Session shown in a real terminal, and fails for any that the workstation does not then name as the agent of that session. And it finds each again after a stop and a start; behind a locked gate an installer leaves nothing, and the capture holds the probe's packets alone. Another starts programs put under the home by hand, by their names, in a Terminal Session: each runs as the agent's user in `/workspace`, the shell is there again when it quits, and closing the session ends everything started in it. A third puts stand-ins under agents' names, a node script, a python script, a program of its own and a shell script, starts each by typing, and reads what the workstation says runs in the session: the first three are the agents they are named for, the shell script and `vi` are none, a session is a shell's again when its agent quits, and one session's agent says nothing of another.

**Agents at work** are tested with real models (`integration/agentwork_test.go`). One test installs each of the seven agents in one sandbox behind an open gate, tells each of a model as its maker's documentation says, in its own file or its environment, and starts each by its name in a Terminal Session, with a prompt typed after it: write a file, then raise your hand. It fails for any agent whose file is not there, or whose hand the app was not told of for the session it was typed in. So each one's model was reached through the gate, each one ran what its model asked, and each one found `raise_hand` in its own registry, where the supervisor wrote the server `sandbox`: nothing else told it. Every model is asked through [OpenRouter](https://openrouter.ai) with the experiments' key, and is a cheap one: its maker's own where the agent's maker makes models (Claude Haiku 5.5 for Claude Code, GPT-6 Luna for Codex, Grok 4.3 for Grok, Kimi K2.5 for Kimi Code, Gemini 4 Hydrogen for Antigravity), and the experiments' DeepSeek V4.1 Flash for OpenCode and Pi, whose makers make none. Antigravity speaks the Gemini API alone, which OpenRouter does not answer: the test starts the **Translator** (`integration/testdata/gemini_translator.py`) in the workstation, which answers that API on the workstation's loopback by asking OpenRouter, and names it to Antigravity as its endpoint. The key is in the `~/.bashrc` of that sandbox's Home, as you would put it there, and in the Translator's environment; the Home is deleted with the sandbox. A job that was not done is given once more, a cheap model not always doing as it is told; and the capture must hold what the gate lets pass and nothing else. Without `.env` the test is skipped. It costs a few cents.

The **ACP Bridge** is tested in four places. What crosses is tested with no Docker (`internal/acpbridge`): every method of the protocol's first version both ways, each with members it does not have, `_meta` among them; a login that runs a command, by its type and under `_meta`; a name twice in an object, and names in another case; the rules of ids; lines that are no message and lines too long; paths with `..`, with a folder whose name only begins as the Shared Folder's, with separators written as `%2F` and with another host; that what an agent is refused is said in none of the app's words; that the package imports the core and the standard library's text alone; and a property that is fuzzed: whatever either side sends, no `_meta` crosses and no path that is not in the Shared Folder. That the agent is started by one fixed text, with its arguments as words whatever they hold, and that ending its session ends its processes, are the supervisor's tests; that only a running workstation that was started with an ACP Bridge and mounts a Shared Folder gets an agent, the orchestrator's, against a daemon of the tests' own; that the command is the first thing the app's executable does, the root's. Against Docker (`integration/acpbridge_test.go`) the test is the ACP client: it builds the app's executable as it is shipped and starts it with a data directory of its own. A scripted agent, put in the workstation under an agent's name, asks its client for `/etc/passwd`, for a file to be written and for a terminal, offers a login that runs a command, and reports files in and outside the Shared Folder; the client must see none of the first, sees the files in the folder by this Mac's path and no other, and the agent wrote down what it was given: nothing of this Mac. The workstation's processes are counted before, and are as many again after the client closes, after the bridge is killed and after the sandbox stops.

Two more are **experiments** of it. One starts OpenCode by the bridge, driven by a real model with the experiments' key, which is in the `~/.bashrc` of that sandbox's Home as its user would put it there, and gives it a job as an ACP client does: the file is in the Shared Folder, and every path the client was told of is in it. The other installs each agent the app knows with its maker's installer, and the program by which Claude Code and Codex speak the protocol, and has the bridge start each by the command written beside its name: it fails for one that does not answer `initialize`, and asks no model anything.

Eight tests need a virtual Interface, where a sandbox is seen at another address than this Mac's physical exit address. They open a gate on that address, run two sandboxes on two Interfaces at once, and they lose the virtual Interface under a running download four ways: it goes away and the sandbox is allowed no other; it goes away with this Mac's physical Interface allowed after it, and comes back; it stays up and begins to lead to this Mac's physical Interface; it stays up and goes silent. The seventh expects any exit address but a physical one there, with the real Host Watchdog: the gate opens on the virtual Interface's exit address with nothing listed, locks for Physical Exit Address Unknown when the Watchdog forgets what it read, as it does when the Mac wakes, and locks on the mismatch when the Interface begins to lead to this Mac's physical Interface. The eighth expects this Mac's physical exit address there, which the virtual Interface's is not: the gate stays locked on the mismatch and nothing but the probes leaves; when the Interface is made to lead to this Mac's physical Interface the gate opens, at this Mac's physical exit address, and it locks again when the Interface leads to the virtual Interface's exit address again. Its owner makes that Interface. It is not in this repository, nor is anything that makes such an Interface: the fixture is one gitignored file, `integration/virtualinterface_fixture_test.go`, the only reader of the gitignored `instance_test`, where its owner wrote down what the fixture needs. Making an Interface takes root, which the tests neither have nor ask for: the fixture says what to start, and while that is not running those tests skip. Each of those four changes the Interface only once the sandbox has been seen leaving by it with its download running, and watches where the internet sees the sandbox throughout; the test of the Interface that leads elsewhere reports for how long that was this Mac's own address.

Three more need a second exit address behind the same Interface, to which the fixture makes it lead as an exit **drifts**: the Interface stays up, with its name and its address, and what leaves by it comes out at another address. They skip where the fixture has one exit address. A drift either ends the connections that were made before it or leaves them where they were made, and each test says which. The first drifts to an address that is not expected, with a Hold and without: the gate locks on the mismatch, the download gets no further, and a Hold keeps nothing. The second drifts to an address that is expected too, listed beside the first or covered by any but physical: the gate stays open there and back. The third stalls the virtual Interface, by which no new connection is then made while the ones that were made go on: without a Hold the download is cut when the lease runs out, and with one it is still running when probes are answered again. From inside, a test counts the answers a sandbox got and where they said it was. A request that left and was not answered before the lock, it does not see.

A **Hold** is tested on this Mac's physical Interface, with the probes silenced between the TUN device and the Carrier while one address is let across. Under a download the gate locks and says that it holds, the download goes on, and a new connection and a name query are refused, until the Hold is over and the download is cut; a Host Condition that stops holding ends it at once. That nothing the sandbox sends leaves under a Hold is tested on a connection a server keeps open: a request on it is answered under the open gate, a second one under the Hold gets no answer though its packets cross to the Carrier, and is answered on the same connection once the gate is open again, which it is from under the Hold, by probes that were carried meanwhile. With the Carrier's wait taken out, that test fails. Another holds the Probe Source Ports on the VM's kernel: under an open gate a connection of the sandbox's from one of them is refused, one from the port beside them is answered, and a server in the sandbox still listens on one, on loopback.

The **lease trace** (`integration/leasetrace_test.go`) is no test of what must hold: it counts. It runs only where `ZEOLITE_LEASE_TRACE` says for how long, and then keeps a sandbox open by this Mac's physical Interface and one by the virtual Interface, takes from each word of the gate when the probe was sent that renewed the lease and when its answer came, and says how often and for how long a lease of each duration would have run out: counted from when the probe was sent, and counted from when the answer came. Beside each it runs a sandbox that keeps a Hold, and counts how often its lease did. The margin of that lease (`sandbox.HoldLeaseMargin`) was chosen from it.

One test is **the experiment**: a real model, run by opencode in a sandbox that leaves by the virtual Interface, is asked to work, to find out where it is, and to get out. It needs the fixture and an [OpenRouter](https://openrouter.ai) API key in `.env` at the root of the repository, which is gitignored too:

```
OPEN_ROUTER_API=<the key>
```

```sh
go test -tags integration -timeout 30m -v -run 'TestVirtualInterface|Experiment' ./integration/
```

It gives the model four things to do: answer a fixed prompt; find its public address three ways; learn all it can about the machine that hosts it, by names, gateways and scans; and keep a download going while the test takes its Interface away. Every verdict comes from the TUN capture, from a listener on this Mac and from files, never from what the model says of itself. The key is in no sandbox's config: it is in the environment of each command that runs opencode there, under the name opencode looks for, `OPENROUTER_API_KEY`. The test logs what the model wrote, with the key and the addresses the sandbox is seen at taken out, and saves nothing. It costs a few cents. Without `.env` or the fixture it skips.

## What was checked, and what was not

Checked on 26 November 2026, on the same Mac, macOS 15.5, an Apple M4, Xcode 16.4, Blender 5.1.2 and Homebrew's Python 3.14, for what an audit of the Host Tool Wall said of it, and for the Allowed Applications:

- **The audit, tried again from inside the Wall as it was**, with a program of Python's and one in C, each run under the Wall's own text and again with no Wall. What it said held: a link at the top of `/Applications` that leads into the home was read, and the home's path with it; 129 of Homebrew's 131 receipts held that path, and two files that start a package's service, which it had not counted; the hardware's registry was walked from its root, 1,967 entries, each with its name, and 1,329 services were found by matching, each with its class and its number; the kernel's network policy opened. On two things it was wrong. It said that no profile can keep a tool from walking the registry: one can, by refusing the messages to the kernel that ask it, as one of the system's own profiles does, and with the first of them refused a tool had no root to walk from. And it said that no address of this Mac's leaked: a socket, which a tool can make though it sends nothing on it, answered the address of an interface.
- **What it had not found**, by the same probes. One call returned the name the user logged in under. Another returned where a file is for the numbers of its volume and of the file, with no path for a rule to govern: of the 400 numbers next to one file's, 82 named a file in the home, so that by counting a tool had the name of every file on this Mac's disk, though it could open none of them. A tool made shared memory, a semaphore and a queue of the kind this Mac's programs share by a number, and could neither use nor remove what it made, which stayed until it was removed by hand; one made outside the Wall it was refused. And with the GPU, the properties allowed for the graphics device were answered by every device: 564 of the 1,329 services told their class, 200 classes among them.
- **Each closed, and tried again.** The probes went into the tests first and were run against the Wall as it was: six lines that the test wants refused were done. With the Wall changed each is refused, and the same program with no Wall does every one. The receipt and the service file were read under the Wall as it was and are refused now, with their package's folder listed as before. The registry's program, built with `cc` under the Wall: without the GPU every question refused; with it, a device found by its class, and no walk, name, place, class, number, parent or child, nor a class by a property, which only the graphics device and its surfaces answer now: 2 services where there were 564. Without this Mac's name Blender ended at its start, as the docs say it does.
